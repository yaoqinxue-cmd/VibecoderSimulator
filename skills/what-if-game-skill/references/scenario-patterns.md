# Scenario Patterns

Use these patterns to avoid generic advice. Pick the closest pattern, then adapt it to the user's actual situation.

## Free Growth vs Paid Validation

Common illusion:

- Growth looks like validation.

Hidden costs:

- Cost grows before willingness to pay is clear.
- Free users can blur the real buyer profile.

Early signals:

- Who would pay if asked today?
- Do active users repeat the core action?
- Does usage increase cost faster than learning?

Useful branch set:

- Keep free growth.
- Introduce small paid test.
- Reduce scope before pricing.

## Content Momentum vs Product Stability

Common illusion:

- Attention feels like product-market fit.

Hidden costs:

- Public promises create support debt.
- Persona can outrun product reality.

Early signals:

- Are new users completing the core action?
- Are support questions repeating?
- Does content attract the user you actually want?

Useful branch set:

- Publish now.
- Stabilize before publishing.
- Publish a narrower honest build log.

## Full-Time Jump vs Part-Time Validation

Common illusion:

- More time automatically creates more clarity.

Hidden costs:

- Cash pressure can distort product judgment.
- Identity pressure rises after public commitment.

Early signals:

- Current weekly progress with limited time.
- Paid demand before full-time.
- Runway in months, not vibes.

Useful branch set:

- Go full-time now.
- Keep part-time and run a time-boxed validation.
- Negotiate a staged transition.

## Enterprise Customer vs Product Boundary

Common illusion:

- A large customer means the product is validated.

Hidden costs:

- Custom work can become a hidden service business.
- Roadmap control shifts toward one buyer.

Early signals:

- How many requested features help other users?
- Can the pilot be scoped tightly?
- Are support and deployment expectations explicit?

Useful branch set:

- Promise enterprise version.
- Run a bounded pilot.
- Say no and stay self-serve.

## Full Rewrite vs Local Repair

Common illusion:

- A clean architecture will solve unclear product pressure.

Hidden costs:

- Rewrite delays learning.
- New architecture can hide old uncertainty.

Early signals:

- Is the pain concentrated in one boundary?
- Do bugs repeat in the same area?
- Can one local fix unlock delivery?

Useful branch set:

- Full rewrite.
- Local repair.
- Keep shipping and document pain points.

## Automate Everything vs Keep First-Hand Judgment

Common illusion:

- Faster processing means better understanding.

Hidden costs:

- User voice gets abstracted away.
- The system can optimize around the wrong categories.

Early signals:

- Do you still read raw feedback?
- Can you name the user's exact words?
- Are automated summaries changing decisions?

Useful branch set:

- Automate all intake.
- Automate draft, human review.
- Read small raw samples before automation.

## Scope Expansion vs Narrow Entry

Common illusion:

- A bigger roadmap makes the product feel more real.

Hidden costs:

- Every added surface area creates more unfinished states.
- A wide first version delays the moment when one user can succeed end to end.
- The team starts discussing platform shape before the first habit exists.

Early signals:

- Can a new user explain the product in one sentence?
- Is one workflow becoming smoother week by week?
- Are bugs spread across many features instead of concentrated in one core path?

Useful branch set:

- Build the broader platform now.
- Cut back to one entry point.
- Keep the vision document but ship one narrow workflow.

## User Vote vs Product Positioning

Common illusion:

- The loudest requested feature is the clearest market signal.

Hidden costs:

- Votes reward visible wants, not necessarily repeated needs.
- A small group can pull the roadmap away from the product's center.
- Saying yes too often teaches users that the product has no spine.

Early signals:

- Do voters use the current core action repeatedly?
- Would the requested feature help the target user or just the loudest user?
- Can you explain why a feature is not being built without sounding defensive?

Useful branch set:

- Follow the vote.
- Say no and explain the product boundary.
- Run a small manual test before committing the roadmap.

## Data Dashboard vs Human Observation

Common illusion:

- More metrics automatically create more understanding.

Hidden costs:

- Dashboards can name where people drop off without showing why.
- Instrumentation work can delay watching one real user struggle.
- Teams may debate charts instead of fixing a visible broken step.

Early signals:

- Can you describe the exact moment users hesitate?
- Are the same drop-offs appearing in recordings or interviews?
- Does a new metric change a decision, or just decorate uncertainty?

Useful branch set:

- Add more tracking.
- Watch a few real sessions.
- Use metrics to pick where to observe, then inspect that moment manually.

## Community Growth vs Structured Feedback

Common illusion:

- A busy community means the product is learning faster.

Hidden costs:

- Support, moderation, and expectation management become invisible work.
- Loud conversations can bury the most useful product signals.
- The product roadmap starts being pushed by social energy.

Early signals:

- Are community messages turning into repeated product insights?
- How much time goes into moderation versus product work?
- Do quiet high-value users have a way to give feedback?

Useful branch set:

- Open a community now.
- Start with a structured feedback form.
- Invite a small user circle with clear discussion prompts.

## Brand Polish vs Functional Proof

Common illusion:

- A sharper name, logo, and landing page will make the product feel validated.

Hidden costs:

- Brand work can hide that the core action still feels uncertain.
- Public positioning hardens before user learning is complete.
- The product begins performing maturity it has not earned.

Early signals:

- Can users complete the core action without explanation?
- Does the landing page promise something the product cannot yet do?
- Are people praising the look while failing to repeat the behavior?

Useful branch set:

- Polish brand and website now.
- Stabilize the core action first.
- Write a plain promise, then only polish what the product can prove.

## Delegation vs Founder Judgment

Common illusion:

- Giving work away always increases leverage.

Hidden costs:

- Delegation without clear standards creates review debt.
- The founder can lose first-hand contact with the most important details.
- A helper may optimize for task completion, not product learning.

Early signals:

- Can the delegated task be judged without reading the founder's mind?
- Are review comments repeating the same missing standard?
- Is delegation freeing judgment time or creating coordination drag?

Useful branch set:

- Delegate the whole area.
- Keep direct ownership for now.
- Delegate drafts or operations while keeping final judgment close.
